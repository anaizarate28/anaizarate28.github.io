# Self-Assessment
Throughout my time in this program, I've learned and have become skilled in different areas of coding and problem solving. From the beginning of the program, making a project work seemed like the entire objective, rather than diving deep into it and enhancing it to what it could become. In this course, I analyzed and improved my earlier work with the goal of making improvements based on everything I had learned throughout the program. In my assignment for CS 499, I started to consider my previous work in a different way. Of course, good software is not only about getting the right result, but also about decisions made regarding design, data management, and long-term maintainability.

In this program, I used Git, which was more useful for learning about collaborating with others than I anticipated. It also made me think about how I could arrange my work, and create meaningful commits, where I wrote what I changed and reasoning behind it. It was important to me that the other developers should be able to follow a history of a project without asking the initial developer. That same habit of making the work of other people easier to them was expanded upon by presentations, written assignments, documentation and code reviews throughout the program. For the project, I did a walk-through of my project and explained my design decisions as if my project were being reviewed for the first time by a developer, treating the instructor's feedback as I would a reviewer's comments.

Making that work clear was just as important when the stakeholder wasn't familiar with what's going on. For some projects I had to defend technical decisions when the person making the decision was more interested in what would happen than how things would happen, which would make me have to convert my design decisions into reliability, usability, or cost terms, rather than code structure. Learning how to make that case, and how much technical detail to include depending on who was deciding whether a course of action was worth taking, was part of my learning curve, alongside coding itself.

Technical growth in areas such as data structures, algorithms, software engineering, and databases came from learning how these areas work together rather than studying them separately. In general, there are many ways to solve a problem, but some solutions are better than others. My project reflected this directly: swapping a Cursor-based lookup for an item model backed by a list held in memory cut down how long it took to locate and order inventory entries, while also leaving the code more approachable to revisit later. My database coursework helped me understand SQL and how different types of data can be related. Together, these experiences helped me better understand how to build a complete application rather than focusing on individual parts.

Security became something I built into that process rather than checked for afterward. Analyzing C++ programs for vulnerabilities and comparing insecure code against safer alternatives using CERT guidelines taught me to look for weaknesses while a program was still being developed. In the assignment, that mindset showed up in how I checked incoming data before storing it, kept queries from being built out of raw text, took care of how passwords were stored, and made sure schema changes wouldn't wipe out data that already existed. CS 410 pushed that same instinct further, working with C++ and x86-64 assembly and using tools like GDB and objdump to understand how programs actually behave at a lower level, which made me more comfortable investigating a problem directly instead of guessing at its cause.

Three artifacts, all built around that same item tracker application, are what this ePortfolio uses to tie these skills together. The Software Design and Engineering artifact reflects how I restructured the application's internal structure. The Algorithms and Data Structures artifact reflects the item-model and in-memory approach described above, along with the resulting gains in lookup and ordering speed. The Databases artifact reflects how the application's data is organized through linked tables. Together, they show how these different areas of computer science reinforce one another within a single application. Finishing the program has made me more confident in my ability to learn new technologies, solve problems, communicate with both technical and non-technical audiences, and improve on existing software, skills I plan to keep building as I move into the field.

# Algorithms and Data Structures
Inventory Management App

The artifact is an Android application that manages inventories that I developed in CS 360, and I chose it for Algorithms and Data Structures because it shows that I can improve efficiency and maintainability. I added an InventoryItem class and stored the information in an ArrayList<InventoryItem> to make it possible to sort the inventory by name, by quantity and to be able to search the inventory live without having to query the database again and again. These enhancements illustrate the application of suitable data structures, separation of data access from presentation and efficient processing of data in accordance with the Course Outcomes that I outlined in Module One. The learning outcome of this enhancement is the understanding of how selecting the right data structure can make it easier to add new features and make it more efficient. The most difficult part was maintaining consistency of the in-memory list with the database following edits, this was a reinforcement of the need for consistent data throughout an application.

# Databases
Inventory Management App

In the Databases enhancement for my item tracker app, I took the inventory table from my Android app and created a section for each piece of info to better identify items and their information such as what it is, who makes it, what group does it belong to, and a log of every change. To ensure that the new structure really did perform as expected, I used a sample csv file to avoid having to manually type in a few test entries, and wrote some multi-table lookups so that the app could retrieve an item, its group, and its supplier in a single query, rather than three. After loading in a much larger set of records like this, it became a bit difficult to page through the list, and the display started lagging. I'm still working on making the display scroll properly and am investigating the lagging aspect when the number of records increases. In general, it made me start thinking a bit more carefully about how a schema should be arranged, how tables should be linked to each other and how a design decision made at database level can have an impact from the bottom up. What remains is to fix the lag and go through a full cycle of testing it and comparing the final product to what the course outcomes actually require.
